Run a cocotb testbench against RTL sources through Icarus Verilog (default) or
Verilator, reporting a per-test passed/failed/skipped breakdown plus optional
Verilator coverage -- see docs/cli/functional-verification.md for the
request/response contract and the CLI surface. Phase 3 of Epic #391, and the
hard gate behind `klt eval`'s `valid` field (#387). Invoked exclusively
through cocotb 2.0's first-party Python `Runner` API, never a generated
Makefile; the verdict is always derived from the run's own `results.xml`,
never from a simulator's exit code. Requires cocotb (`pip install cocotb`)
plus an `iverilog` or `verilator` binary on `$PATH`. `options.coverage`
requires `engine: "verilator"`. Takes a request document (like `klt lvs`/`klt
sim`), not positional RTL file args.

positional arguments:
  request klt functional-verification request: a path to a JSON file, '-' to read the request from stdin, or an inline JSON object string. Relative paths inside the request resolve against the request file's own directory (stdin/inline: the cwd); --base-dir overrides that anchor

options:
  -h, --help show this help message and exit
  --base-dir DIR resolve every relative path in the request (sources, testbench module/search_path, options.includes, options.sdf.file, options.initial_state.netlist, options.source_defines keys) and the default `.klt/functional-verification/` artifact directory against DIR instead of the request file's own directory -- e.g. re-run a request archived beside its evidence record from the directory its paths were written against (a file request with --base-dir D resolves exactly as the same document piped on stdin with cwd=D). Default: the request file's directory (stdin/inline: the cwd). Must exist and be a directory
  --mutations PROPOSALS_PATH run mutation testing (issue #1592): a path to a <proposals> JSON document (schema klt.functional_verification.mutation_proposals/1) naming byte-exact source mutations to apply, one at a time, to an isolated build+test of the same <request>. Aborts with exit 1 if the request's own baseline run fails first -- see docs/cli/functional- verification.md, '--mutations' (example below)
  -o, --outdir OUTDIR write run artifacts (results XML, logs, simulator build directory, coverage, trace, mutants/) here instead of `.klt/functional-verification/` next to the request file; created if missing, relative paths resolve against the cwd. Request-relative source paths still resolve against the request's own directory (or the --base-dir override)
  --pdk PDK PDK variant to resolve a request.pdk block's cell models from (e.g. sky130A); overrides request.pdk.variant (issue #5782)
  --pdk-root PDK_ROOT explicit PDK install root; overrides $PDK_ROOT and the search order
  --format {text,json} output format (default: text)

--mutations <proposals> example (every required field filled):
{
  "schema": "klt.functional_verification.mutation_proposals/1",
  "scope": [ "<a path from request.sources, byte-for-byte>"
  ],
  "proposals": [ { "index": 1, "category": "operator", "file": "<same string as in scope>", "line": 10, "original_code": "<the byte-exact source line>", "mutated_code": "<the replacement line>" }
  ]
}
`index` is 1-based and unique; `scope` entries and `file` must repeat a `request.sources` string exactly.
All validation errors are reported in one run.
Full field table: docs/cli/functional-verification.md
