# `row-mix-gf180/` — a generic mixed-device, shared-diffusion, fixed-pitch layout

A small gf180mcu cell (14 transistors, 8.00 × 10.41 µm) with unlike devices
sharing diffusion, a fixed pitch, supply continuity and ports at caller-chosen
x, plus the independent checks that grade it. It is the `row_mix_gf180` example
from [`docs/design/custom-transistor-layout-study.md`](../../docs/design/custom-transistor-layout-study.md)
§4.1, prepared for issue #3969.

**What this is not.** It is not a row engine, router or new `klt` verb, and it is
not evidence that one is justified (see
[What this does and does not establish](#what-this-does-and-does-not-establish)).
`generate.py` is a one-off, example-local script.

## What is drawn

Two diffusion rows (N, W = 0.8 µm; P, W = 1.6 µm, in an Nwell) between a VSS
rail with p+ substrate tie and a VDD rail with n+ well tie; 0.28 µm gates at a
0.8 µm node pitch. The netlist is inverter → transmission gate → NOR3 → inverter
plus one off dummy gate per row:

| Row | Diffusion islands (nets on each node) |
| --- | --- |
| N | `VSS n1 n2` · `ny VSS ny VSS` · `VSS Y VSS` |
| P | `VDD n1 n2` · `VDD p1 p2 ny` · `VDD Y VDD` |

Facing source/drain nodes of neighbouring devices are one diffusion shape.
Series nodes `p1`/`p2` carry no contact at all. Orientation is **derived**: each
device is flipped when its right terminal matches the previous node (the
transmission gate and the second inverter are declared drain-first and drawn
flipped). A mismatch between facing nets with no explicit `BREAK` is a hard
error. The two `BREAK`s in the N row are alignment breaks so N and P gates share
columns and common-gate poly; the N row could have shared `VSS` across the
second one.

Routing is Metal1 for gate pads/bars and supply stubs, Metal2 for diffusion-net
verticals and the `ny` trunk. **Every routing coordinate is hand-chosen** (see
`GATE_TRACKS`, `NET_ROUTES`, `GATE_LINKS`).

## Study §4.2 requirements: achieved, partially, or not

| Requirement | Status |
| --- | --- |
| Unlike-device chain (inverter → TG → NOR3) | Achieved |
| Determinism (two runs, identical sha256) | Achieved; tested, and the committed GDS equals a regeneration |
| Device/connectivity equivalence, independent of the generator | Achieved: LVS `match` (14/14 devices, 13/13 nets, 8/8 pins); per-device L/W of the extraction compared with the hand-written netlist within 1 dbu; a 1 dbu width change in the reference makes LVS mismatch |
| Supply continuity | Achieved: one `VSS` net, one `VDD` net, `split_net_labels: []`; dropping a VSS strap makes LVS fail |
| Fixed pitch | Achieved: outline width = 8.00 µm = the requested pitch; a mirrored copy abuts with shared rails and extracts to one `VSS`, `VDD` and `S` net |
| Pitch "smaller than the isolated layout, so sharing is required" | Achieved: legal minimum 7.84 µm; the same devices as isolated two-contact islands need 10.08 µm |
| Ports at caller-specified x, one off the routing grid | Achieved: `A` 0.80, `C` 4.80 (on the 0.40 µm routing grid), `B` 3.17 (off-grid); extracted label positions equal the requests |
| Control net continues across the abutment | Achieved for `S` (an edge-to-edge Metal1 line) |
| Two same-net supply rails needing an explicit strap (#3920) | **Not achieved as specified.** One rail per supply, strapped per node; the unstrapped case is tested instead |
| Obstacles avoided "with computed clearance" | **Not achieved.** Clearance is by construction at hand-picked coordinates; there is no computed-clearance step |
| ~20 devices | 14 here (including 2 dummies); kept small enough to review by hand |

## Verification receipts (executed in this PR)

All three on one backend, curated gf180mcu deck, in-process `klayout.db`, no
standalone KLayout and no PDK install:

- **`klt drc` curated deck: `clean`, 0 violations**, 43 rules checked, 71
  inapplicable to the geometry. This is **not** full coverage: the report's
  `coverage.unmodeled_rules` lists 74 rules the deck does not transcribe
  (gf180mcu `DF.*_MV`, `MT.2b`/`MT.3`/`MT.4`, `MT30.*`, `MSLOT.*`, …). The
  wide-metal and narrow-line end-of-line classes are not in that list either,
  which is what #3968 is about. Poly-to-contact spacing is likewise not modeled;
  the 0.15 µm gap is by construction, not checked.
- **`klt extract`**: 14 devices (7 nfet, 7 pfet), 13 nets, 8 pins.
- **`klt lvs`** (`klayout` engine) against `row_mix_gf180.sp`: `match`. The one
  warning is a `bjt` device class with no devices on either side.

## Study §4.3 failure cases

| # | Case | Status |
| --- | --- | --- |
| 1 | Different nets on facing diffusions | Tested: `facing_net_mismatch`, naming the device pair |
| 2 | Pitch below the minimum legal width | Tested: `pitch_below_minimum`, with the deficit in dbu (7.0 µm → 840 dbu) |
| 3 | Two ports closer than the metal pitch | Tested: `ports_too_close`, naming both. The 0.53 µm threshold is conservative: it assumes ports share a column, which these Metal1 pads do not |
| 4 | Netlist device with no row assignment | Tested: `unassigned_device` |
| 5 | Wide metal at curated spacing | Curated half characterised; native half **deferred** (above) |

Errors are raised as `RowError` with a stable `code`. They are Python exceptions
in this example, not `klt` JSON-envelope errors; no new verb exists.

## What this does and does not establish

**Generic (reusable idea):** the chain solver (`solve_chain`, about 40 lines:
orientation derivation, `BREAK`, facing-net error), the node/gate x arithmetic
(0.8 µm pitch from L + contact + poly-contact gap), the pitch lower bound, the
four validation errors, and the check set (extract → LVS → curated DRC → double
run → abutment).

**Block-specific (hand-chosen here):** the device list and row assignment, where
`BREAK`s fall, all channel track heights, which nets use a vertical versus a
trunk, how gates reach diffusion nets, the dummy-gate tie-offs and the port set.
Routing is most of the code, and none of it is derived from rules.

**For a future row builder:** one hand-drawn, self-authored example shows a
shared-diffusion row can be drawn and checked headless with existing tools. It
does **not** satisfy the study's Stage 2 gate (§6.2) by itself:

- (a) a shared reference from the reporter's generator: not obtained;
- (b) a second consumer with the same need: not identified;
- (c) use of a rules-derived pitch helper (#3972): the pitch here is a literal;
- (d) a CI-runnable independent oracle: the curated half runs in CI (see the
  test); the native-deck half does not.

Stage 2 and any general router stay gated. If (a) never materialises, the study
already names the fallback: this example plus the "draw with `klayout.db`, then
run `klt drc/lvs/extract`" recipe.
