# Design pipeline worked example: sky130 5T OTA reference buffer

A worked example for [Epic #105](https://github.com/2AMLogic/klayout-tools/issues/105)
Phase 3 (issue #130): drive one small sky130 block through every
**non-blocked** stage of the staged agent design pipeline defined in
[`docs/design/design-pipeline.md`](../../docs/design/design-pipeline.md)
(Phase 1, PR #114) using the per-stage skills under `.claude/skills/`
(Phase 2, PRs #127/#128/#129).

The original bring-up stopped at S6/S10-schematic: S7 (layout generation), S8
(DRC/LVS) and S9 (extraction) had no `klt` verb to reach for. Epics #152
(`klt gen`), #191 (`klt gen-compose`) and #153 (`klt extract`/`klt lvs`) closed
those gaps, and Epic #153 phase 4 (issue #164) ran S7 → S8 → S9 →
post-extraction S10 against this block's own sized devices. Everything through
S10 now runs; S11 is the one remaining stub.

**Block:** a five-transistor OTA (`kb:five-transistor-ota`) used as a
unity-gain follower buffering a 1.8 V reference node onto a 1 pF
switched-capacitor sampling load. Chosen for spec fit against the KB entry,
not familiarity — see [`04-topology.json`](04-topology.json).

Regenerate the schematic-level (S6/S10) netlist and request JSON with:

```sh
uv run python3 examples/design-pipeline/generate.py
uv run klt sim examples/design-pipeline/sim-ac.request.json --format json
uv run klt sim examples/design-pipeline/sim-op.request.json --format json
```

Regenerate the whole back end (S7 → S8 → S9 → post-extraction S10) with:

```sh
uv run python3 examples/design-pipeline/generate-layout.py
```

[`generate-layout.py`](generate-layout.py) both writes the request documents
and runs the chain (`klt gen` ×3 → `klt gen-compose` → `klt drc` →
`klt extract` → `klt lvs` → `klt sim`), because every S7–S10 artifact there is
a tool output rather than a hand-authored stage record.

(Both require a resolvable sky130A PDK — `klt pdk find --pdk sky130A` — and
`ngspice` on `PATH`.) The committed `*.result.json` files were captured
by running exactly these commands; their `runtime_s` and
`environment.engine_version` fields are machine-dependent and will not
reproduce byte-for-byte, but the pass/fail verdicts and measured values
should.

## S7–S10 results (post-layout: generation, DRC/LVS, extraction, post-extraction sim)

This is the back half of the loop, run for the first time in this example.
Everything below is reproduced by
[`generate-layout.py`](generate-layout.py).

### S7 — layout generation

Three `klt gen` blocks, sized directly from
[`05-sizing.json`](05-sizing.json) (not from `docs/cli/gen-compose.md`'s
illustrative worked example):

| S5 device(s) | W/L (µm) | Generator | `params` |
| --- | --- | --- | --- |
| M5 tail + M5b bias replica | 10/1 | `mos_array` | `rows: 1, cols: 2, dummy: 0, topology: "array", w_um: 10, l_um: 1` |
| M1/M2 input pair | 8/0.5 | `diff_pair` | `mirror: false, splits: 1, add_guard_ring: false, w_um: 8, l_um: 0.5` |
| M3/M4 mirror load | 6/1 | `diff_pair` | `mirror: true, splits: 1, add_guard_ring: false, w_um: 6, l_um: 1` |

M5b is realized as the second device of the tail array rather than as its own
block: M5/M5b are a 1:1 matched pair in S5's own sizing (`mirror_ratio`
`"1:1 (M5b:M5)"`), which is exactly what `mos_array` exists to draw. Row-major
`topology` puts the replica at `U0` (west) and the tail device at `U1` (east),
so `U1_D` faces the differential pair placed to its east — the orientation
`klt gen-compose`'s two-pin router needs (#199).

`klt gen-compose` then places them in one row and routes four two-pin nets
([`07-layout.result.json`](07-layout.result.json)) — composed cell
`ota_5t_top`, bbox 9.26 × 16.4 µm, `unrouted_nets: []`:

| Net | Pins | Routed length (µm) |
| --- | --- | --- |
| `TAIL_A` | `tail.U1_D` → `diffpair.Q1_1_S` | 2.42 |
| `TAIL_B` | `tail.U1_D` → `diffpair.Q2_1_S` | 8.82 |
| `N1` | `diffpair.Q1_1_D` → `mirror.M1_1_S` | 2.42 |
| `VOUT` | `diffpair.Q2_1_D` → `mirror.M2_1_S` | 4.42 |

`TAIL_A`/`TAIL_B` decompose the three-way tail node (M5 drain + both input
sources) into two two-pin nets sharing the `tail.U1_D` endpoint, since >2-pin
bundle routing is out of scope for `klt gen-compose` today.

### S10 (post-extraction) — corner sweep against the extracted netlist

[`ota_5t_post.spice`](ota_5t_post.spice) `.include`s
`ota_5t_extracted.spice` **unmodified** and instantiates its `.SUBCKT`,
driving each signal pin from a supply-referenced resistive divider
(`N1 = 2/3 vdd`, `VOUT = 1/2 vdd`, `TAIL = 1/4 vdd`). Sweep: 2 supplies ×
3 temperatures = 6 corners. [`sim-post.result.json`](sim-post.result.json):
`status: "pass"`, 6/6 corners, 0 errored.

| Measurement | Limit | Worst case | Corner |
| --- | --- | --- | --- |
| `n1_ratio` (v(N1)/v(vdd)) | 0.660–0.674 | 0.665732 (margin +0.0057) | `default/1.980V/125C` |
| `vout_ratio` (v(VOUT)/v(vdd)) | 0.495–0.505 | 0.499299 (margin +0.0043) | `default/1.980V/125C` |
| `tail_ratio` (v(TAIL)/v(vdd)) | 0.245–0.255 | 0.248277 (margin +0.0033) | `default/1.620V/125C` |

Raw pin voltages are reported without limits (`vdd_meas`, `n1_v`, `vout_v`,
`tail_v`) and track the supply as expected — e.g. at `1.620V/-40C`:
1.62 / 1.08 / 0.809999 / 0.404999 V.

### What the post-extraction pass does and does not prove

**Does prove**, on the real extracted netlist, with no hand editing and no
`$N` node names addressed out of band:

- Every `connectivity[]` net `klt gen-compose` routed is addressable from a
  `klt sim` testbench as a named `.SUBCKT` pin.
- Those pins are mutually **isolated** — the divider ratios only hold if no
  two pins are shorted through the layout. This check has teeth: shorting `N1`
  to `VOUT` in the testbench (a stand-in for a routing bug) drives both ratios
  to ≈0.571 and fails 6/6 corners.
- The chain is fully headless and JSON-contracted end to end.

**Does not prove**: the S3/S10 electrical specs (`gain_db`, `ugf`, `pm_deg`,
`isup_ua`, `vout_dc`) re-verified post-layout. Three gaps stand between this
pass and that, all filed rather than worked around — see "Friction" below.

## Friction encountered

**S6/S5 Loop A pass 1: a testbench-methodology failure that looked like a
sizing failure.** The first open-loop AC characterization attempt (netlist
without the DC feedback network) failed `gain_db` at 3 skewed corners
(worst 19.3 dB vs. the 30 dB target). This was not a device-sizing
deficiency: the naive testbench let the output float to a
corner-dependent DC balance point that drifted toward a rail at skewed
corners, pushing a load device into triode and collapsing measured gain —
an artifact of how open-loop gain was characterized, not of the sizing.
Fixed by adding a DC feedback network (`Lfb`/`Cfb` in
[`ota_5t.spice`](ota_5t.spice)) that holds `out = vcm` at DC while opening
the loop at AC, with no sizing change. See `05-sizing.json`'s
`loop_a_history` for the full record.

Neither the `design-netlist-authoring` (S6) nor `design-sizing` (S5) skill
mentions this technique, even though it is the standard way to
characterize open-loop gain for an amplifier intended for closed-loop
(unity-gain) operation — without it, an agent following the skills as
written would burn one or more Loop A "sizing" iterations chasing a gain
shortfall that isn't a sizing problem at all. Filed as follow-on friction:
[#142](https://github.com/2AMLogic/klayout-tools/issues/142).

No other friction was hit in the S1–S6/S10 (schematic-level) run: S7/S8-LVS/S9/S11
behaved exactly as their skills documented **at the time** (explicit stubs,
correctly identified before attempting any workaround), and #54's existing
tracking already covered that gap per the `design-extraction` skill's own
"comment there rather than filing a duplicate" guidance — a comment was left
on #54 rather than opening a new issue for the same gap. S7–S9 are no longer
stubs; the friction found running them for real is below.

### S7–S10 (post-layout) bring-up

The chain itself ran without manual intervention. Three gaps stand between the
post-extraction pass this run produced and a real "simulation-verified"
closure of the loop; each is filed rather than worked around:

- **[#208](https://github.com/2AMLogic/klayout-tools/issues/208) — no PMOS
  device flavor.** No `klt gen` generator takes a device-type parameter, so
  the PMOS mirror load (M3/M4 in [`05-sizing.json`](05-sizing.json)) draws
  NMOS geometry and extracts as `nfet`. The composed layout is topologically
  the 5T OTA at the right sizes, but it is not the circuit
  [`ota_5t.spice`](ota_5t.spice) describes — which is also why
  [`ota_5t_reference.spice`](ota_5t_reference.spice) has to declare all six
  devices `nfet` for LVS to match.
- **[#209](https://github.com/2AMLogic/klayout-tools/issues/209) — extracted
  netlists carry deck class names, not PDK model names.** `klt extract` emits
  `M ... nfet` cards; sky130A defines `sky130_fd_pr__nfet_01v8` as a
  `.subckt`, so the PDK model library cannot be bound and
  [`ota_5t_post.spice`](ota_5t_post.spice) has to supply
  `.model nfet nmos level=1`. This is also why `sim-post.request.json` has no
  `corners.process` axis — a process sweep would be decorative here, so it is
  omitted rather than faked.
- **[#210](https://github.com/2AMLogic/klayout-tools/issues/210) — unrouted
  generator ports carry no labels.** #200 labelled the nets `klt gen-compose`
  routes; a port not listed in `connectivity[]` still extracts as an anonymous
  `$N` net. All six gates fall in that bucket, so no device in the composed
  circuit can be biased — hence `.options rshunt=1e12` in the post-extraction
  testbench (a documented convergence aid, per #205) and measurements limited
  to pin addressability/isolation.

Two smaller, already-tracked items were re-confirmed rather than re-filed:
[#205](https://github.com/2AMLogic/klayout-tools/issues/205) (`klt sim`'s
singular-matrix classification and invalid `.meas op`; the documented
`analysis.kind: "tran"` + `rshunt` workaround is what this example uses) and
[#201](https://github.com/2AMLogic/klayout-tools/issues/201) (the unused
device class now reported as a `warning`, visible in
[`08-lvs.result.json`](08-lvs.result.json)).
