# Spike: geode-fem WASM + WebGPU feasibility

**Status:** spike / findings. Nothing here is scheduled, and nothing here
authorises implementation. Per
[docs/ARCHITECTURE.md](../ARCHITECTURE.md) → "How capabilities arrive," a
major capability arrives by spiking first — survey, real evidence, and a
build/wrap decision — filed before implementation starts. This is that
spike for Epic #840 Phase 2 (issue #889), mirroring the shape of
[docs/design/wasm-spice-playground-spike.md](wasm-spice-playground-spike.md),
which took the SPICE playground spike → playground.

The question: **can a subset of
[rjwalters/geode-fem](https://github.com/rjwalters/geode-fem) compile to
WASM+WebGPU and reproduce one Phase-1 validated benchmark in the browser?**

---

## Findings summary, ahead of the detail below

Three findings, in descending order of surprise:

1. **The WASM half works — completely, today, with two small upstream
   patches.** geode-fem's `geode-core` compiles to **`wasm32-unknown-unknown`**
   (the browser target), the patch-antenna benchmark's driven solve **runs**
   in a V8 WASM engine, and it reproduces the committed Phase-1 export
   (`examples/em/patch_antenna/patch_antenna.em-export.json`) to a **maximum
   relative error of 6.8e-14** across `Z_in`, `S11`, `P_in`, `P_rad` — i.e.
   double-precision agreement, not "close enough." Payload: **3.89 MB raw /
   969 KB gzip / 699 KB brotli**, with the 1 MB tetrahedral mesh already
   `include_bytes!`-embedded. This is real, measured, reproducible evidence
   (§3), not a survey claim.

2. **The WebGPU half does not, and the reason is architectural, not a
   toolchain gap.** `geode-core --features wgpu` *type-checks* on
   `wasm32-unknown-unknown` (burn-wgpu 0.21 / cubecl-wgpu 0.10 / wgpu 29 all
   compile for the web target — §4.1). But it buys nothing for this
   benchmark, for two independent reasons:
   - **The patch-antenna solve never touches a Burn backend for the
     expensive part.** `driven_solve_with_ports`'s default path assembles on
     Burn tensors and then hands a `faer` `SparseColMat<usize, c64>` to
     `sp_lu()` — a **host-side, CPU, sparse-LU direct solve**. Profiling the
     native run puts the hot leaf in `gemm_c64::microkernel::neonfcma`, i.e.
     faer's complex dense GEMM microkernel inside the numeric factorization
     (§4.2). Switching Burn's backend to wgpu moves the *assembly* tensors to
     the GPU and leaves the dominant cost exactly where it is.
   - **WebGPU has no f64, and geode-fem's oracles are f64-calibrated.**
     `cubecl-wgpu` registers `FloatKind::F64` **only** behind
     `wgpu::Features::SHADER_F64`, which wgpu-types documents as *"This is a
     native only feature. Supported Platforms: Vulkan"* and lists in the
     native-only feature mask. A browser WebGPU adapter never exposes it, so
     `burn::backend::Wgpu<f64>` — the exact type `geode-core`'s own
     `testing::TestBackend` selects under `--features wgpu` — cannot be
     realised in a browser (§4.3). geode-fem has already litigated this class
     of problem once, in its own `flex_precision_spike` (issue #451, Epic
     #374): every non-ndarray Burn backend is statically f32, and the
     eigen/driven oracles need f64.

3. **So the epic's premise — "Burn → wgpu/WebGPU is what makes geode-fem
   browser-viable" — is inverted.** WebGPU is the part that does *not* work;
   plain single-threaded WASM is the part that works perfectly. The honest
   framing for any follow-up is "geode-fem in the browser **on the CPU, in
   WASM**," and the real cost question is not GPU access, it is **20 s per
   frequency point** (§5).

**Verdict: DEFER, with a narrow build option.** See §8.

## 1. What "the solver subset" actually is

Phase 1's patch-antenna export is generated by
`examples/em/patch_antenna/generate.py` driving geode-fem's own
`cargo run -p patch_antenna --release` benchmark binary. The minimal subset
needed to reproduce **one frequency point** of that benchmark's S-parameter
sweep is:

| Piece | geode-fem API | Notes |
| --- | --- | --- |
| Fixture load | `geode_core::mesh::read_patch_fixture()` | The mesh is **already** `include_bytes!("../../tests/fixtures/patch_2g4.msh")` (`crates/geode-core/src/mesh/patch.rs:126`) — no filesystem access, which is exactly what a browser needs. 4750 nodes / 25 452 tets / 30 635 edges, `sha256 01c55cbd…f05f83` (matches the Phase-1 export's `provenance.geometry.fixture_sha256`). |
| PEC mask | `pec_interior_mask_from_triangles` over patch + ground + outer triangles | Pure host code. |
| Port | `PatchFixture::port().lumped_port(50 Ω/η₀, 1+0j)` | Pure host code. |
| Materials | `PatchFixture::matched_upml_materials(FR4_MATERIALS, …, ω)` | Rebuilt per ω (box-UPML stretch is ω-dependent). |
| Solve | `geode_core::driven::solve::driven_solve_with_ports::<B>` | The whole assembly + factorization + back-solve. |
| Extraction | `port_voltage` / `port_current` / `driven::extraction::s11` / `driven::scattering::flux_power_box` | Pure host code. |

That is **five modules of `geode-core` and no other workspace crate.**
Notably *not* needed: `geode-app` (clap harness), `geode-util` (only used
for a unit conversion and the `.vtu` viz reconstruction — see §6, it is a
trap), the eigen solvers, ARPACK, `spade`, and every example binary.

The reproduction probe is ~110 lines mirroring
`examples/patch_antenna/src/main.rs::run_sweep` for a single ω. It is
scratch, built outside both repos, and is **not** committed here (this
issue ships no code — §7); the full source is reproduced in §9 so anyone
can re-derive these numbers.

### 2.1 Blocker A — `getrandom` has no default `wasm32-unknown-unknown` backend

```
$ cargo check -p geode-core --target wasm32-unknown-unknown --no-default-features
error: The wasm32-unknown-unknown targets are not supported by default;
       you may need to enable the "wasm_js" crate feature.
  --> getrandom-0.4.2/src/backends.rs:176:17
error: could not compile `getrandom` (lib) due to 1 previous error
```

`getrandom 0.4` arrives transitively and non-optionally:

```
getrandom v0.4.2
└── rand v0.10.1
    ├── burn-backend v0.21.0 → burn-tensor → burn-core → burn v0.21.0
    └── … → geode-core
```

**Fix (2 lines, upstream):** enable `getrandom`'s `wasm_js` feature for the
wasm target and set `--cfg getrandom_backend="wasm_js"` in
`.cargo/config.toml`. In this spike that was done from the driver crate
(feature unification puts it in the same dep graph) plus:

```toml
# .cargo/config.toml
[target.wasm32-unknown-unknown]
rustflags = ['--cfg', 'getrandom_backend="wasm_js"']
```

Not needed for `wasm32-wasip1` (WASI supplies `random_get`).

### 2.2 Blocker B — `faer`'s `rayon` feature drags in `atomic-wait`, which has no wasm port

```
$ cargo check --target wasm32-unknown-unknown   # after fixing A
error[E0433]: cannot find module or crate `platform` in this scope
  --> atomic-wait-1.1.0/src/lib.rs:28:5
   |
28 |     platform::wait(atomic, value)
error: could not compile `atomic-wait` (lib) due to 3 previous errors

$ cargo tree -i atomic-wait
atomic-wait v1.1.0
└── spindle v0.2.6
    └── faer v0.24.4
        └── geode-core v0.3.0
```

`spindle` is `optional = true` in faer's manifest and is pulled in **only**
by faer's `rayon` feature — so this should have been switched off by
`--no-default-features` (which disables `geode-core`'s `faer-parallel`).
It is not, and that is an upstream bug worth naming precisely:

> **`faer/rayon` is enabled unconditionally by the workspace dependency
> line, not by `geode-core`'s `faer-parallel` feature.** `Cargo.toml`
> declares
> `faer = { version = "0.24", default-features = false, features = ["std", "linalg", "rayon"] }`
> at the workspace level, and per-crate `features` are *unioned* with the
> workspace base. `faer-parallel = ["faer/rayon", "dep:rayon"]` is therefore
> a no-op for faer (it still correctly gates the direct `rayon` dep and the
> `ParallelismGuard`), and `cargo build -p geode-core --no-default-features`
> does **not** produce the "strictly single-threaded faer" the feature's own
> doc comment promises.

**Fix (1 line, upstream):** move `rayon` off the workspace base line and
onto `geode-core`'s `faer-parallel` feature, i.e.

```toml
# workspace Cargo.toml
faer = { version = "0.24", default-features = false, features = ["std", "linalg"] }
```

With that one-line change applied to a scratch copy of the tree,
`geode-core` checks clean on `wasm32-unknown-unknown`:

```
$ cargo check --target wasm32-unknown-unknown
   Checking geode-core v0.3.0 (…/crates/geode-core)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 2m 30s
```

### 2.3 Blocker C — `geode-util` re-enables `geode-core`'s default features

A first attempt at the reproduction probe depended on `geode-util` (just
for `units::ghz_to_omega_mm`) and blocker B came back:

```
faer feature "rayon"
  └── geode-core feature "faer-parallel"
      └── geode-core feature "default"
          └── geode-util v0.3.0
```

`geode-util`'s `geode-core = { workspace = true }` carries default features,
so **any** consumer that also uses `geode-util` gets `faer-parallel` back
regardless of its own `default-features = false`. Worked around in the probe
by inlining the two-line unit conversion; the real fix is upstream (§6, U-3).

## 3. The result: a Phase-1 benchmark point, reproduced in WASM

Two WASM targets were built and run, both from the same probe source:

| Target | Artifact | Runner |
| --- | --- | --- |
| `wasm32-wasip1` | 3.41 MiB `.wasm` binary | `node v26.7.0` + `node:wasi` preview1 |
| **`wasm32-unknown-unknown`** (the browser target) | 3.89 MB cdylib `.wasm` | `node v26.7.0`, `WebAssembly.instantiate` with 4 stub imports, calling the exported `solve_patch_point(f_ghz) -> *const f64` directly |

| `z_im_ohm` | `1.74962526987718050e+01` | `1.74962526987716274e+01` | 1.02e-14 |
| `s11_re` | `-7.47588515360355199e-01` | `-7.47588515360361194e-01` | 8.02e-15 |
| `s11_im` | `5.96627455309733490e-01` | `5.96627455309730381e-01` | 5.21e-15 |

**Max relative error: 6.79e-14.** For reference, the same probe built

floating-point contraction/`libm` differences, not from a precision loss.

**Stated tolerance for the acceptance criterion: `rel_err ≤ 1e-12` on every
scalar figure of merit. Measured worst case 6.8e-14 — passes with ~4 orders
of margin.**

| 2.5 | `1.5926623801150572` / `1.592662380115` | `-0.5315833655532743` / `-0.531583365553` |

## 4. Why WebGPU is the part that does not work

### 4.1 The wgpu backend *compiles* for the web target

This much of the epic's premise is true, and it was verified, not assumed:

```
$ cargo check --target wasm32-unknown-unknown   # geode-core features = ["wgpu"]
    Checking wgpu-types v29.0.4
    Checking burn-cubecl v0.21.0
    Checking burn-wgpu v0.21.0
    Checking burn v0.21.0
    Checking geode-core v0.3.0
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 5m 26s
```

Burn's wgpu backend and its whole cubecl/wgpu stack are `wasm32`-clean. If
the solver's hot path were Burn tensor ops, this would be the good news the
epic expected.

### 4.2 …but the patch-antenna hot path is `faer` sparse LU on the host

`driven_solve_with_ports`'s default `SolverMode::Direct` assembles the
complex pencil `A(ω) = K(ν) + iωC(σ) − ω²M(ε) + Σ_p (iω/Z_p)S_p` and then
does a **direct sparse factorization on the CPU**:

```rust
// crates/geode-core/src/driven/solve.rs
use faer::sparse::{SparseColMat, Triplet};
…
SparseColMat::<usize, c64>::try_new_from_triplets(n_interior, n_interior, &triplets)
    …
    .sp_lu()
…
lu.solve_in_place(fwd.as_mut());
```

Sampling the native run (`sample`, 6 s window) puts the dominant leaf in
faer's complex dense GEMM microkernel — the supernodal panels inside the
numeric factorization:

```
Sort by top of stack, same collapsed (when >= 5):
  gemm_c64::microkernel::neonfcma::c64::cplx_x3x4    99
  faer::sparse::linalg::solvers::SymbolicLu<I>::try_new   5
  ndarray::iterators::to_vec_mapped                       5
```

Two consequences:

- **Selecting `--features wgpu` would not move this work to the GPU.** It
  changes the Burn backend used for *assembly*, not the `faer` factorization
  that dominates. A WebGPU build of this benchmark would be a GPU-accelerated
  assembler feeding a CPU direct solve — the transfer-bound anti-pattern
  geode-fem's own `solver/ksp_burn.rs` module header calls out explicitly.
- **The `neonfcma` leaf is an aarch64 NEON complex-FMA kernel.** On wasm32
  it degrades to scalar code (wasm SIMD128 is off by default), which is
  most of the measured 2.6× WASM-vs-native-single-thread slowdown (§5).

geode-fem *does* have a genuinely GPU-resident path —
`SolverMode::IterativeMatrixFree`, a complex-symmetric COCG whose Krylov
vectors are split-complex Burn tensor pairs over a matrix-free Nédélec
operator (`solver/ksp_burn.rs`, `driven/matrix_free.rs`, issue #302). That
is the only architecture in the repo for which "WebGPU" is even a coherent
proposition. It is not what the patch-antenna benchmark uses, and porting
the benchmark onto it is an upstream change of substantial size that would
also change the numbers (iterative vs direct) — see §6, U-5.

### 4.3 …and WebGPU cannot carry the f64 the oracle is calibrated against

`geode-core`'s `testing::TestBackend` selects `burn::backend::Wgpu<f64>`
under `--features wgpu`. That type only means anything if the runtime
registers f64:

```rust
// cubecl-wgpu-0.10.0/src/backend/wgsl.rs:102
if feats.contains(wgpu::Features::SHADER_F64) {
    props.register_type_usage(ElemType::Float(FloatKind::F64), TypeUsage::all());
}
```

and `SHADER_F64` is documented in `wgpu-types-29.0.4/src/features.rs`:

```
/// Enables 64-bit floating point types in SPIR-V shaders.
///
/// Note: even when supported by GPU hardware, 64-bit floating point operations
/// are frequently between 16 and 64 _times_ slower than equivalent operations
/// on 32-bit floats.
///
/// Supported Platforms:
/// - Vulkan
///
/// This is a native only feature.
const SHADER_F64 = 1 << 33;
```

It is a **native-only** feature (it appears in the crate's native-only
feature mask), gated on Vulkan's `shaderFloat64`. The WebGPU browser API
does not expose it and WGSL has no `f64` type at all. So on a browser
adapter, `Wgpu<f64>` cannot register f64 type usage, and the only available
GPU precision is f32.

This is not a new problem for geode-fem: its own
`crates/geode-core/examples/flex_precision_spike.rs` (issue #451, Epic
#374) documents that `Backend` is implemented only for the default f32
instantiation on non-ndarray backends, that a naive backend swap loses
precision at the host upload boundary (`Vec<B::FloatElem>` = `Vec<f32>`),
and that the eigen/cube-cavity oracles need f64 to hit their `1e-6` bounds.
The Phase-1 patch-antenna export was, correspondingly, generated on
`burn::backend::NdArray<f64, i32>` — the export's own `provenance.generator.backend`
field says so:

> `"burn::backend::NdArray<f64, i32> (CPU; no GPU feature compiled …)"`

An f32 WebGPU solve would not reproduce the 6.8e-14 agreement in §3; it
would need a *new*, looser tolerance and a *new* argument that the answer is
still physically right. That is a research question, not an integration
task.

## 5. Performance: the real cost question

Single 2.0 GHz frequency point, same probe, same fixture:

| Build | Threading | Solve wall time |
| --- | --- | --- |
| Native aarch64, `faer/rayon` on | multi-core | **3.43 s** |
| Native aarch64, `faer/rayon` off | single | **7.52 s** |
| `wasm32-wasip1` under node/V8 | single | **~18–21 s** (18.0 / 20.5 / 19.7 / 19.6 s across runs) |
| `wasm32-unknown-unknown` under node/V8 | single | **20.1 s** |

Payload and memory for the browser-target module:

| Metric | Value |
| --- | --- |
| `.wasm` raw | 3 890 413 B (3.71 MiB) |
| gzip -9 | 969 254 B (947 KiB) |
| brotli -q 11 | 698 697 B (682 KiB) |
| `WebAssembly.compile` | 15–19 ms |
| linear-memory high-water | **596–630 MiB** |

Reading these numbers against the epic's stated interaction ("tweak
geometry → re-solve → see the field update"):

- **Payload is a non-issue.** 682 KB brotli is *smaller* than the SPICE
  playground's accepted 5.75 MB gzip engine bundle, and it already includes
  the 1 MB mesh.
- **Memory is a caution, not a blocker.** ~610 MiB of wasm32 linear memory
  is under the 4 GiB wasm32 ceiling but is a lot to ask of a phone; a tab
  OOM is a plausible failure mode on low-memory devices and would need a
  capability check.
- **Latency is the blocker.** 20 s for one frequency point, ~4.4 minutes
  for the committed 13-point sweep, on a single thread, with no
  cancellation story. That is not "tweak and re-solve"; it is a batch job in
  a tab. For contrast, the SPICE playground spike accepted its build on a
  measured **sub-second to ~1 s per re-run**.

Two levers exist and neither is small: **wasm SIMD128** (`-C
target-feature=+simd128`, measured in §5.1) and **wasm threads**
(`wasm32-unknown-unknown` + atomics + `SharedArrayBuffer` + COOP/COEP
headers on klayout-tools.org, plus a faer/rayon story that currently
cannot even be switched off correctly — §2.2).

### 5.1 SIMD128 measured — no help

The cheap lever was tried, not assumed:

```bash
RUSTFLAGS="-C target-feature=+simd128" cargo build --release \
    --bin geode-solve-probe --target wasm32-wasip1
```

| Build | `.wasm` size | Solve wall time (2 runs) |
| --- | --- | --- |
| `wasm32-wasip1`, scalar | 3.41 MiB | 18.0 s / 20.5 s |
| `wasm32-wasip1`, `+simd128` | 3.60 MiB | 20.2 s / 20.8 s |

**No measurable speedup.** The explanation follows directly from §4.2: the
hot leaf is `gemm 0.19`'s hand-written complex microkernel family
(`neonfcma` on aarch64, AVX variants on x86), and `gemm` ships no wasm-SIMD
microkernel — so `+simd128` only exposes autovectorization of the generic
scalar fallback, which LLVM does not usefully vectorize for a complex
supernodal panel update. Results still match the oracle
(`z_re_ohm` rel. err 6.88e-14, `s11_re` 4.60e-15) — the last-digit shift
versus the scalar build is fp-contraction noise, well inside the §3
tolerance.

The consequence for §5's "two levers": **one of them is already spent.**
Getting the browser solve materially under 20 s means wasm **threads**
(atomics + `SharedArrayBuffer` + COOP/COEP cross-origin isolation on
klayout-tools.org + a working faer/rayon feature story, which does not exist
today — §2.2), or a smaller fixture (§10), or a different solver mode
(U-5). None of those is a small change.

## 6. Required upstream geode-fem changes (candidate issues)

klayout-tools builders cannot make cross-repo changes, so these are
enumerated as candidates for [rjwalters/geode-fem](https://github.com/rjwalters/geode-fem),
in the order a WASM build would need them. U-1 through U-3 are small and
independently valuable; U-4 onward are the ones that make this an epic.

**U-1 — Move `rayon` off the workspace `faer` line onto `faer-parallel`.**
*(bug, ~1 line + CI lane)* The workspace base
`faer = { …, features = ["std", "linalg", "rayon"] }` unions into every
consumer, so `geode-core`'s `faer-parallel` feature cannot actually disable
faer's rayon and `--no-default-features` does not produce the
"strictly single-threaded" build its own doc comment promises. Side effect:
`spindle` → `atomic-wait` breaks every `wasm32` target. Fix is to drop
`rayon` from the workspace line (each consumer already opts in via
`faer-parallel`). *Independently valuable*: it makes the documented
single-threaded correctness-gate baseline real.

**U-2 — Make `wasm32` a supported target for `geode-core`'s
`--no-default-features` build.** *(enhancement)* Enable `getrandom`'s
`wasm_js` feature and ship the `--cfg getrandom_backend="wasm_js"` rustflag
for `wasm32-unknown-unknown` (a `.cargo/config.toml` entry), and add a
`cargo check --target wasm32-unknown-unknown --no-default-features` CI lane
so it does not silently rot. With U-1 this is the entire "does it compile"
story.

**U-3 — Stop `geode-util` from re-enabling `geode-core`'s default
features.** *(bug)* `geode-util`'s `geode-core = { workspace = true }`
carries defaults, so any consumer of `geode-util` gets `faer-parallel` back
even with `default-features = false`. Should be
`{ workspace = true, default-features = false }` with an explicit feature
re-export, matching the pattern `geode-core`'s own dev-dependency
self-reference already uses (and documents the reason for).

**U-4 — A no-I/O, no-clap "solve one point" library entry point.**
*(enhancement)* The patch-antenna benchmark's physics currently lives in
`examples/patch_antenna/src/main.rs` (fixture wiring, UPML geometry, flux
box, port extraction) interleaved with `std::fs`, `std::process::Command`
(for `sha256sum`), and clap. A browser consumer needs that ~110-line core
as a library function on `geode-core`/a new `geode-bench` crate, returning
the row DTO. Without it every consumer re-derives the benchmark setup by
hand — which is precisely what this spike had to do, and is a correctness
hazard (get `SIGMA_0`, `PML_THICK`, or `FLUX_SHRINK` wrong and the numbers
silently drift).

**U-5 — Decide whether the browser path is `SolverMode::Direct` (CPU faer)
or `SolverMode::IterativeMatrixFree` (Burn/GPU).** *(design)* These are
different products. Direct+CPU is what reproduces Phase-1 bit-for-bit and
what this spike measured; matrix-free+Burn is the only path for which
"WebGPU" means anything, but it is f32 on any browser adapter (§4.3), has
no calibrated tolerance against the Phase-1 oracle, and would need its own
validation campaign. Nothing else on this list is worth doing until this is
answered.

**U-6 — f32 tolerance study for the driven patch benchmark.** *(research,
blocked on U-5 choosing the GPU path)* If WebGPU is genuinely wanted, the
prerequisite is an answer to "what does the patch-antenna S11 sweep look
like in f32, and is it still physically right?" — the f32-vs-f64 analogue
of what `flex_precision_spike` did for the eigen path. Until that exists,
"WebGPU field solve in the browser" has no oracle.

**U-7 — wasm threads build story.** *(enhancement, blocked on U-1)* If the
CPU/WASM path is chosen, the only remaining perf lever is
`wasm32-unknown-unknown` + atomics with a `wasm-bindgen-rayon`-style pool —
`-C target-feature=+simd128` was measured and does nothing (§5.1), because
`gemm 0.19` has no wasm-SIMD microkernel. Threads require cross-origin
isolation (COOP/COEP) on the host site, which is a klayout-tools-side
constraint rather than a geode-fem one, *plus* U-1 (today faer's rayon
cannot be controlled by feature at all). A `gemm` wasm-SIMD microkernel
would be the alternative, but that is an upstream-of-upstream change.

## 7. Out of scope for this spike / what was NOT changed

- **No production site changes.** `site/` is untouched; #890 / #891 / #892
  remain gated on this verdict, exactly as the issue requires.
- **No dependency added** to `site/package.json` or `pyproject.toml`, no
  `klt` verb touched, no `.wasm` staged into `site/public/`.
- **No changes to geode-fem.** Every patch in §2 was applied to a
  throwaway `rsync` copy of the checkout under `/tmp`; the real
  `~/GitHub/geode-fem` working tree was only read. The patches are written
  up as candidate upstream issues in §6 instead.
- **No browser run.** Everything was executed under node v26's V8 — the
  same WASM engine family as Chrome, but not a browser tab. A real-browser
  run (and a real WebGPU adapter query) is the first thing any follow-up
  should do, exactly as the SPICE playground spike flagged for itself.

## 8. Build / wrap / defer

Applying [docs/ARCHITECTURE.md](../ARCHITECTURE.md) → "Rewrite rule" to
the *browser-solve* capability:

1. **Bottleneck or ceiling — partially holds.** Phase 1's pre-computed
   gallery is a real ceiling for interactivity: a visitor cannot change the
   geometry. But the measured browser cost of lifting that ceiling is 20 s
   per frequency point, which replaces "cannot interact" with "interaction
   takes minutes." That is not obviously an unlock.
2. **Oracle exists — holds, strongly.** This is the spike's best news: the
   Phase-1 export is a bit-for-bit oracle, and the WASM build hits it at
   6.8e-14. Any follow-up has a trustworthy regression gate on day one.
3. **Unlock — fails as scoped.** The thing the epic wanted unlocked was a
   *WebGPU* solve. WebGPU cannot supply f64 (§4.3) and would not touch the
   dominant `faer` cost anyway (§4.2). What is actually available is a
   single-threaded CPU solve in WASM — which is a real capability, but not
   the one #840 Phase 2 was written to justify.

**Verdict: DEFER.**

Concretely, the recommendation is:

- **Close out Phase 2 as specified** (#890 "WASM+WebGPU build of a solver
  subset", #892) — the WebGPU framing is not achievable against the Phase-1
  oracle and should not be re-attempted without U-5/U-6 landing upstream
  first. #891 (the non-WebGPU fallback) is unaffected: Phase 1's
  pre-computed results already *are* that fallback and already ship.
- **File U-1, U-2, U-3 upstream now.** They are small, they are bugs
  (U-1/U-3 mis-scope features against their own documentation), they are
  valuable independently of the browser question, and together they are the
  entire "geode-fem compiles to wasm32" story. Landing them keeps the door
  open at near-zero cost.
- **Do not build the browser playground yet.** The one narrow build option
  worth naming, if the operator wants browser interactivity sooner: a
  **"solve one frequency point on demand"** interaction (not a sweep, not
  geometry editing) behind an explicit "this takes ~20 s" affordance and a
  memory capability check, on the CPU/WASM path, cross-checked against the
  Phase-1 export in CI via the tolerance in §3. That is a genuinely
  shippable thing, but it is a *different* issue from #890 and should be
  filed as such after U-1/U-2/U-4 land — not folded into this epic's Phase 2
  by reinterpretation.

The time-box was not the binding constraint here; the physics of WebGPU's
f32-only shader model was. That is a better outcome than running out of
clock, and it is why the recommendation is a confident defer rather than an
"unknown, retry later."

### 9.3 Probe body (the solve, verbatim)

```rust
use burn::backend::NdArray;
use faer::c64;

use geode_core::constants::ETA_0_OHM as ETA_0;
use geode_core::driven::extraction::s11;
use geode_core::driven::ports::{port_current, port_voltage};
use geode_core::driven::scattering::flux_power_box;
use geode_core::driven::solve::{
    CurrentSource, DrivenBcs, DrivenMaterials, driven_solve_with_ports,
};
use geode_core::mesh::patch::FR4_MATERIALS;
use geode_core::mesh::{pec_interior_mask_from_triangles, read_patch_fixture};

type B = NdArray<f64, i32>;

const R_PORT_OHM: f64 = 50.0;      // examples/patch_antenna/src/main.rs
const SIGMA_0: f64 = 25.0;
const PML_THICK_BENCH_MM: f64 = 25.0;
const FLUX_SHRINK: f64 = 0.10;

// Inlined from geode_util::units::ghz_to_omega_mm so the probe does not
// depend on geode-util, which re-enables geode-core's default features
// (and therefore faer/rayon -> spindle -> atomic-wait). See §2.3.
fn ghz_to_omega(f_ghz: f64) -> f64 {
    2.0 * std::f64::consts::PI * f_ghz * 1.0e9 / geode_core::constants::C_MM_PER_S
}

let fixture = read_patch_fixture().expect("read patch fixture");
let edges = fixture.mesh.edges();
let mask = pec_interior_mask_from_triangles(&edges, &[
    fixture.patch_triangles().as_slice(),
    fixture.ground_triangles().as_slice(),
    fixture.outer_boundary_triangles().as_slice(),
]);
let port = fixture.port();
let r_nat = R_PORT_OHM / ETA_0;
let lp = port.lumped_port(r_nat, c64::new(1.0, 0.0));
let source = CurrentSource { j_tet: vec![[c64::new(0.0, 0.0); 3]; fixture.mesh.n_tets()] };

let (air_lo, air_hi) = fixture.air_box(PML_THICK_BENCH_MM);
let center: [f64; 3] = std::array::from_fn(|k| 0.5 * (air_lo[k] + air_hi[k]));
let half:   [f64; 3] = std::array::from_fn(|k| 0.5 * (air_hi[k] - air_lo[k]));
let flux_lo: [f64; 3] = std::array::from_fn(|k| center[k] - (1.0 - FLUX_SHRINK) * half[k]);
let flux_hi: [f64; 3] = std::array::from_fn(|k| center[k] + (1.0 - FLUX_SHRINK) * half[k]);

let device = <B as burn::tensor::backend::BackendTypes>::Device::default();
let omega = ghz_to_omega(f_ghz);
let (eps_t, nu_t) = fixture.matched_upml_materials(
    &FR4_MATERIALS, air_lo, air_hi, PML_THICK_BENCH_MM, SIGMA_0, omega);
let sol = driven_solve_with_ports::<B>(
    &fixture.mesh,
    DrivenMaterials::MatchedUpml { epsilon_tensor: &eps_t, nu_tensor: &nu_t },
    None,
    &DrivenBcs { pec_interior_mask: &mask },
    std::slice::from_ref(&lp),
    omega,
    &source,
    &device,
).expect("driven solve");

let v = port_voltage(&fixture.mesh, &lp, &edges, &sol.e_edges);
let i = port_current(&lp, v);
let z = v / i;
let z_ohm = z * ETA_0;
let p_in = 0.5 * (v * i.conj()).re;
let p_rad = flux_power_box(&fixture.mesh, omega, &sol.e_edges, flux_lo, flux_hi);
let s = s11(z, r_nat);
```

### 9.4 Browser-target runner (node)

The `wasm32-unknown-unknown` cdylib imports only four wasm-bindgen
placeholder functions (js-sys/web-sys arrive transitively via
`burn-std`/`web-time`; the module was **not** run through the
`wasm-bindgen` CLI, so those imports are undescribed). Stubbing them is
enough to reach the solve:

```js
const imports = {
  __wbindgen_placeholder__: {
    __wbindgen_describe: () => {},
    __wbg___wbindgen_throw_bb96b2010945f0bc: (p, l) => { throw new Error(`wasm throw ${p}/${l}`); },
  },
  __wbindgen_externref_xform__: {
    __wbindgen_externref_table_set_null: () => {},
    __wbindgen_externref_table_grow: () => 0,
  },
};
const { instance } = await WebAssembly.instantiate(bytes, imports);
const ptr = instance.exports.solve_patch_point(2.0);
const out = new Float64Array(instance.exports.memory.buffer, ptr, 5);
// [z_re_ohm, z_im_ohm, s11_re, s11_im, residual_rel]
```

A production integration would run `wasm-bindgen` properly and expose a
typed surface instead; the stub form exists here to prove the module links
and solves on the browser target without dragging a bindgen toolchain into
a spike.

## 10. Open questions for any follow-up

- **Real browser, real adapter.** Everything here ran in node/V8. A
  follow-up's first task is a Chrome/Safari/Firefox run plus an actual
  `navigator.gpu.requestAdapter()` feature dump, to confirm from the
  browser's own mouth that `shader-f64` is absent.
- **Low-memory devices.** 610 MiB of linear memory on a phone is a
  plausible OOM. What is the capability check, and what is the fallback
  (Phase 1's pre-computed results — already shipped)?
- **Coarser fixture.** geode-fem ships `patch_2g4_smoke.msh` (169 KB vs
  988 KB). A smoke-grade mesh would cut both memory and solve time
  substantially — but it is *not* the Phase-1 benchmark geometry, so it has
  no committed oracle. Would a smoke-fixture browser solve satisfy #840's
  "real solver output, never illustrative renders" discipline? Probably yes
  (it is still real solver output) but it needs its own provenance story.
- **Cancellation.** A 20 s synchronous solve in a Web Worker is fine; a 20 s
  solve the user cannot cancel is not. `faer`'s `sp_lu` has no interruption
  seam.
