# Running one Loom stage against a local Gitea instance

> **This is a qualification record, not a re-adoption.** The Gitea NO-GO of
> 2026-10-09 (#9792) stands: Gitea is not a production forge for this fleet,
> no Gitea code changed for this run (#9769), and nothing here reopens that
> decision. What this doc records is what actually happens on current main
> when a caller drives **one** role step at a time against a disposable local
> Gitea container — the command sequence that works, the surfaces that
> refuse, and how runtime / model / effort pinning and telemetry marking are
> expressed without a fleet store.

**Volatile facts, verified:** Gitea image `gitea/gitea:1.24.6`; Loom
`main` at `fd450cacc` (`VERSION` 0.20.13), daemon built from that commit and
pinned with `LOOM_DAEMON_BIN`; run date 2026-11-22. The host's installed
daemon was 0.20.8 (`bcb2cd9`) — five versions behind main with
forge-path commits in between, which is why the run pinned a main-built
binary instead of trusting `$PATH`.

## Result in one paragraph

The **mechanical** Gitea path works: container bring-up, workspace install,
label sync, worktree + branch creation, and authenticated `git push` all
succeeded with `LOOM_FORGE_TYPE=gitea` + `GITEA_URL` + `GITEA_TOKEN`. The
**role-step** path does not: all three targeted steps (`/loom:builder 1`,
`/loom:judge 2`, `/loom:doctor 2`) refused before their first write with
`class=failed reason=forge_unresolvable|forge_unreachable`, because the
daemon-side forge surface the targeted-role contract leans on
(`forge check-claim`, the `gh`-shaped gate reads, `forge comment`, the lease
publish) is GitHub-only. Each refusal was clean — no label, lease or comment
was written on the way out. The gaps are filed as #14938, #14939, #14940 and
#14941; until they land, the operator-side workaround for everything after a
refusal is the raw Gitea API (examples below).

## Bring up the disposable instance

```bash
PORT=39876                                    # any free loopback port
docker run -d --name gitea-qual \
  -p 127.0.0.1:$PORT:3000 \
  -e INSTALL_LOCK=true \
  -e GITEA__server__ROOT_URL=http://127.0.0.1:$PORT/ \
  -v gitea-qual-data:/data \
  gitea/gitea:1.24.6

# One admin user and an all-scopes token (disposable instance only —
# `--scopes all` is fine here, use least scope on anything persistent):
docker exec gitea-qual su git -c \
  "gitea admin user create --username loomtest --email loomtest@example.com \
   --password loomtest-pw --admin"
docker exec gitea-qual su git -c \
  "gitea admin user generate-access-token -u loomtest -t qual-run --scopes all"
# -> Access token was successfully created: <TOKEN>

export GITEA_URL=http://127.0.0.1:$PORT
export GITEA_TOKEN=<TOKEN>
alias gapi='curl -s --noproxy "*" -H "Authorization: token $GITEA_TOKEN"'
```

Notes observed during the run:

- New repos are **private** by default, so unauthenticated API reads 404
  ("The target couldn't be found") — a session probing without the token sees
  "repo does not exist", not "auth required" (this is exactly what the
  Doctor step hit).
- `curl` needed `--noproxy '*'` on the run host; the daemon-side Gitea calls
  in `forge-helpers.sh` were not proxy-affected.

## Prepare the consumer workspace

```bash
# 1. Seed a minimal repo and install Loom from the checkout under test:
mkdir -p ~/qual/loom-consumer && cd ~/qual/loom-consumer
git init -b main && echo "# loom-consumer" > README.md && git add -A && git commit -m init
loom-daemon init . --defaults <loom-checkout>/defaults
git add -A && git commit -m "Add Loom configuration"

# (Seeding from an AGENT session: the primary-checkout-mutation guard denies
#  `git commit` on a checkout's default branch during a sweep step — seed the
#  two scaffold commits from a human terminal, or commit from a linked
#  `git worktree` of the fresh repo, which the guard exempts.)

# 2. Create the repo on Gitea, then push. Git-over-http auth needs a
#    credential store OUTSIDE the repo (real secrets never live in a repo):
gapi -X POST $GITEA_URL/api/v1/user/repos -H 'Content-Type: application/json' \
  -d '{"name":"loom-consumer","default_branch":"main"}'
umask 077
printf 'http://loomtest:<TOKEN>@127.0.0.1:%s\n' "$PORT" > ~/qual/git-credentials
git config credential.helper "store --file=$HOME/qual/git-credentials"
git remote add origin $GITEA_URL/loomtest/loom-consumer.git
git push -u origin main

# 3. Sync the Loom label set — the one forge-writing script that works on
#    Gitea out of the box (36 labels created, additive-only):
LOOM_FORGE_TYPE=gitea .loom/scripts/sync-labels.sh

# 4. File the one issue the Builder step will target. create-issue.sh exits 2
#    on Gitea BY DESIGN ("no split GraphQL/REST quota, no equivalent failure
#    mode"), so file through the API and set loom:issue by label id:
gapi -X POST $GITEA_URL/api/v1/repos/loomtest/loom-consumer/issues \
  -H 'Content-Type: application/json' \
  -d '{"title":"…","body":"…","labels":[<id of loom:issue>]}' >/dev/null
```

`loom-daemon init` was run by the run with the **installed** 0.20.8 binary
against **main's** `defaults/` and completed cleanly; the installed-versus-
main daemon drift matters only for the `loom-daemon` subcommands the scripts
call, which is why every step below pins `LOOM_DAEMON_BIN`.

## Common environment for every step

Every step ran from the consumer workspace root with this environment
(unsetting the dispatching session's sweep variables so the child behaves as
a Tier-0 manual-role invocation, not a fleet step):

```bash
env -u LOOM_SWEEP_ID -u LOOM_SWEEP_CLAIM_OWNED -u LOOM_WORKTREE_PATH \
  -u LOOM_AGENT_SESSION_PID -u LOOM_HOOKS_HOME \
  HOME=$HOME PATH=$HOME/.local/bin:/usr/local/bin:/usr/bin:/bin TERM=dumb \
  LOOM_DAEMON_BIN=<loom-checkout>/target/debug/loom-daemon \
  LOOM_FORGE_TYPE=gitea GITEA_URL=$GITEA_URL GITEA_TOKEN=$GITEA_TOKEN \
  LOOM_RUNTIME=claude LOOM_MODEL=sonnet LOOM_EFFORT=low \
  … telemetry vars, see the last section …
```

`LOOM_FORGE_TYPE=gitea` (env tier) is what makes every `forge-helpers.sh`
consumer take the Gitea branch; without it, detection falls through the
remote-URL probe and defaults to GitHub. A pre-flight
`loom-daemon claude-config trust --project-dir <workspace>` silenced the
folder-trust modal for the spawned sessions.

## Run exactly one step and exit

One step is one headless role session — there is no single-stage CLI verb
(and the qualification did not add one):

```bash
.loom/scripts/spawn-claude.sh -p "/loom:builder <N>" --dangerously-skip-permissions
.loom/scripts/spawn-claude.sh -p "/loom:judge <PR>"    --dangerously-skip-permissions
.loom/scripts/spawn-claude.sh -p "/loom:doctor <PR>"   --dangerously-skip-permissions
```

Each invocation selects an OAuth token from the shared pool, execs one
`claude -p` session, and **exits when the role's step ends** — all three
observed sessions printed their `LOOM_STEP_OUTCOME role=… target=…
class=… reason=…` line and returned control to the shell (no watcher, no
daemon registration, nothing left running). This is the Tier-0 surface of
`targeted-role-invocation.md`, driven by an operator instead of the daemon.

## Stage results and the failure table

### Builder — `/loom:builder 1`

Refused at gate 0 (the pre-claim guard), no writes:

```
loom-daemon forge check-claim 1            -> rc=3  "legs 1-3 of the claim
                                             probe are GitHub-only"
loom-daemon forge parent split-state -p 1  -> rc=2  "cannot resolve owner/repo"
gh issue view 1 --comments                 -> "none of this repo's git remotes
                                             point to a known GitHub host"
LOOM_STEP_OUTCOME role=builder target=1 class=failed reason=forge_unresolvable
```

The role prompt treats a `check-claim` exit other than 0/1 as *unanswered —
stop*, which is correct behavior; `--force-claim` only overrides
label/lease/branch legs on GitHub, not the missing Gitea transport. Filed as
**#14938**.

What the rest of the Builder chain does on Gitea when driven by hand
(this is how the run produced a PR for the Judge step to look at):

| Step | Result |
|---|---|
| `worktree.sh 1` | **Works** — branch `feature/issue-1` + worktree created; **lease publish fails** (`publish gh call failed`, exit 2) so the lease is local-only — #14941 |
| commit + `git push -u origin feature/issue-1` | **Works** with the out-of-repo credential store |
| `create-pr.sh` | **Exits 2 by design** ("GitHub App permission-window fallback is GitHub-specific; on gitea open the PR with your forge's own CLI") — raw API below |
| label swap `loom:issue → loom:building` | No script surface on Gitea (`forge_gh_swap_label_rl_safe` is gh-backed) — raw API |

```bash
# The create-pr.sh workaround (title/body/head/base POST, then labels):
gapi -X POST $GITEA_URL/api/v1/repos/loomtest/loom-consumer/pulls \
  -H 'Content-Type: application/json' \
  -d '{"title":"…","head":"feature/issue-1","base":"main","body":"… Closes #1"}'
gapi -X POST $GITEA_URL/api/v1/repos/loomtest/loom-consumer/issues/<PR>/labels \
  -H 'Content-Type: application/json' -d '{"labels":[<loom:review-requested id>]}'
```

### Judge — `/loom:judge 2`

Refused at the kind/state gate (needs one live read of `issues/<PR>`), no
writes. `gh repo view` / `gh api …/issues/2` cannot resolve the Gitea
remote; `loom-daemon pr-queue --role judge` died on
`error parsing --hostname: invalid hostname` (a `host:port` remote is not
parsed); `LOOM_STEP_OUTCOME … class=failed reason=forge_unreachable`. The
session's own suggestion (`GH_HOST`/`GH_TOKEN`) would not help — Gitea is
not gh-API-compatible. Filed as **#14939**.

### Doctor — `/loom:doctor 2`

Run after `loom:changes-requested` was applied to PR 2 by hand (the Judge
could not). Refused at its PR read: `gh pr view` fails, `loom-daemon forge`
answers "gitea is not handled natively; falling back to the caller's shell
path" (and the caller's shell path is `gh`), and its own unauthenticated API
probe 404'd on the private repo. Notably it **did not use the inherited
`GITEA_TOKEN` env** — the role prompts name the repo-local task-credentials file (see `.loom/docs/credentials.md`), not the
env convention — so an authenticated probe never happened.
`LOOM_STEP_OUTCOME … class=failed reason=forge_unreachable`. Filed as
**#14939** (same read-path family; the env-token guidance is in its
proposal).

## Pinning runtime, model profile and effort

All pinning is env-tier — exactly the tiers a caller outside a fleet store
can set — and each was **observed in the run's spawn log**, not asserted from
docs. The log lines, verbatim:

```
spawn-claude: LOOM_SWEEP_CLAIM_OWNED=unset
spawn-claude: model=sonnet (from LOOM_MODEL)
spawn-claude: effort=low (from LOOM_EFFORT)
# LOOM_CLI_START runtime=claude
spawn-claude: using OAuth account 'agent19-2amlogic' (mode=ranked)
```

| What | Env | Contract |
|---|---|---|
| Runtime | `LOOM_RUNTIME` | `spawn-worker.sh` selects `spawn-<runtime>.sh`; unset = `claude` (adapter #1). This run: `runtime=claude`. |
| Model | `LOOM_MODEL` | injected as `claude --model <value>` unless args already carry `--model` (which wins). This run: `sonnet`. |
| Effort | `LOOM_EFFORT` | injected as `claude --effort <value>`, same precedence shape. This run: `low`. |
| Daemon under test | `LOOM_DAEMON_BIN` | every script's `loom-daemon` call resolves through it — the lever that made the run test main instead of the installed 0.20.8. |
| Speed tier | `LOOM_SERVICE_TIER` | `fast` enables fast mode; unused in this run. |

`--model`/`--effort` on the command line outrank the env vars, and unset
means "session default, no flag emitted" — none of the tiers silently invent
a value. Effort is a session-wide default here (the per-rung escalation
ladder is a daemon-path feature, `model-selection.md`).

## Telemetry: keeping a qualification run out of a fleet store

Two facts, both **observed**, one per direction:

1. **Default: nothing is exported.** A bare manual spawn carries no OTLP
   endpoint, and Claude Code emits no telemetry without
   `CLAUDE_CODE_ENABLE_TELEMETRY=1` — the first probe session, run with the
   OTEL endpoint pointed at a local capture listener but **without** that
   switch, produced **zero** OTLP requests. A qualification run outside a
   daemon therefore contributes nothing to any fleet store by default; the
   daemon's relay is the only exporter on fleet paths.
2. **Opt-in is caller-owned and marks the run.** With the caller's own
   endpoint, the child exports there and nowhere else:

   ```bash
   CLAUDE_CODE_ENABLE_TELEMETRY=1 \
   CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1 \
   OTEL_METRICS_EXPORTER=otlp OTEL_LOGS_EXPORTER=otlp OTEL_TRACES_EXPORTER=otlp \
   OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf \
   OTEL_EXPORTER_OTLP_ENDPOINT=http://127.0.0.1:<port> \
   OTEL_RESOURCE_ATTRIBUTES=loom.qual_run=gitea-single-stage,loom.qual.issue=14850
   ```

   The capture listener observed `POST /v1/traces`, `/v1/logs` and
   `/v1/metrics`, and the raw OTLP bodies carried the caller's marker —
   `loom.qual_run=gitea-single-stage` present as a resource attribute with
   `service.name=claude-code` — so the run's spans are distinguishable from
   fleet data by exactly the attribute the caller set. No Loom-side
   telemetry change is needed for either direction; that is the answer to
   "how is such a run marked": by the caller's `OTEL_RESOURCE_ATTRIBUTES`,
   not by anything in the repo.
